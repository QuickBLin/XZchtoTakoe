# Протокол расширенного эксперимента

Производственный вариант прототипа зафиксирован: символьные и словесные признаки лексики, C=4, оба порога из предыдущей версии. Сравниваются словарь, логистическая регрессия только на словах, только на символах и на их объединении. Для двух альтернатив пороги выбираются только на validation по тому же правилу. Команда `python experiment.py --lock` читает только train и validation. Хешируются входные данные, политика и код эксперимента.

Набор test из версии 1 служит регрессионной проверкой. Новый stress проверяет перенос на описания с опечатками, смесью языков, косвенными симптомами, отвлекающими подробностями и запросами для оператора. Всего 48 однозначных (по 8 на каждую тему), 24 спорных (по 8 смешанных, вне каталога и расплывчатых). В каждом из четырёх однозначных подтипов по 12 заявок. Эталон задаётся по предметным правилам до первого запуска. Отдельно проверяются уникальные ID и точные дубли после нормализации. Набор синтетический и целенаправленно сложный.

Первичная метрика классификации — macro-F1 на известных классах. Дополнительные — точность, precision/recall/F1 по классу и матрица ошибок. Для маршрутизации считаются точность всех очередей, количество и точность автоназначений, число корректно оставленных оператору и число неверных автоназначений в каждой группе. Условие «нет ошибок» применяется только для выбора двух порогов на малой validation и не переносится на итоговые наборы.

Проверка кода включает полезный результат для однозначной заявки, отказ от автоперевода, ручную смену, фильтр, сохранение, формат CSV, полное отклонение невалидного пакета, повторный импорт, откат транзакции при нарушении уникальности, выгрузку и доступ к старой базе. Для времени вывода фиксируются медиана и 95-й процентиль пяти проходов по stress после предварительных прогнозов, без обучения, GUI и SQLite. Время измеряется локально и используется как характеристика стенда, не как производственный норматив.

Рабочие параметры после просмотра stress не меняются. Любое последующее изменение алгоритма проверяется на новом закрытом наборе. Скриншоты работы делаются из запускаемого приложения или тестового окна. Снимок интерфейса подтверждает конкретное состояние, а сохранённые команды и их вывод позволяют повторить запуск.
