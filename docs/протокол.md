# Протокол итоговой проверки

1. При создании данных выделяем отдельные CSV для обучения, настройки и проверки. Одинаковые ID и одинаковые нормализованные тексты запрещены во всех частях. Близкие по смыслу случаи возможны. Категория в столбце label задаётся по предметной инструкции и не входит в признаки текста.
2. Базовый метод считает отдельные совпавшие слова и фразы. Отсутствие признаков или ничья означает ручную проверку. Список фиксируется до итоговой проверки.
3. Основной метод заранее фиксируем как TF‑IDF по словам/парам слов и символьным фрагментам 3–5 букв, затем многоклассовая логистическая регрессия с C=4. Словари, IDF и веса учатся на train.
4. На validation подбираем минимальную оценку и минимальный отрыв. Из сетки выбираем пару с наибольшим числом автоматических назначений при нуле неверных автоматических назначений. При равенстве приоритет у большего порога оценки, затем отрыва. Настройка не открывает test.
5. На test сначала проверяем классификацию 6 классов на однозначных примерах. Для ключевых слов отказ означает ошибку на однозначном примере. Основная метрика macro‑F1 по шести классам, дополнительная accuracy.
6. Затем на полном test оцениваем итоговую очередь по 7 вариантам, включая ручную проверку. Считаем accuracy маршрута, macro‑F1, покрытие (все автоназначения / все заявки), долю верных автоназначений (верные / автоназначения) и число правильно удержанных спорных заявок.
7. После первого запуска серии итоговой проверки сохраняем результаты и анализируем ошибки без обратной подстройки. Для проверки улучшенной версии нужен новый тест. При сравнении держим один и тот же набор у обоих методов.
8. Отдельно проверяем полный сценарий «ввод → классификация → очередь → журнал → решение оператора», сохранение между запусками и отказ от пустого ввода.
